# P0 角色、权限、范围与审批矩阵

> 2026-11-06，P0-04 设计基线。Keycloak 管登录凭据，Organization 管成员与授权，资源所属服务作最终检查。角色模板可以配置，以下不是不可更改的代码枚举。

## 1. 默认角色模板

| 角色 | 允许的能力 | 默认数据范围 | 必须独立授予 / 不默认允许 |
| --- | --- | --- | --- |
| WorkspaceOwner | 工作区设置、成员治理、订阅 / 模块配置 | 当前工作区 | 过账、付款、独立审批和税务收据签发 |
| AccessAdministrator | 邀请、普通角色及范围管理 | 被授权工作区 | 敏感权限转授、自行扩大范围、最后管理员移除 |
| SalesOperator | 客户、报价、销售单制单与提交 | 本人 / 分配部门 | 审批自己的单据、正式过账、任意退款 |
| SalesApprover | 销售审批与履约许可 | 分配部门 | 修改已审批版本、财务过账 |
| PurchasingOperator | 供应商、采购制单与提交 | 本人 / 分配部门 | 自批采购、直接付款 |
| PurchasingApprover | 采购审批与收货授权 | 分配部门 | 仓库确认替代实际收货、财务付款 |
| WarehouseOperator | 指定仓库预留执行、收发、盘点制单 | 分配仓库 | 越仓操作、直接更改余额 / 成本 / 总账 |
| InventoryApprover | 指定仓库调整 / 调拨审批 | 分配仓库 | 审批自己创建的敏感调整 |
| Accountant | 科目 / 税务设置、财务单据制单、对账准备、报表 | 被授权工作区 | 以角色本身绕过独立过账 / 付款复核 |
| FinanceReviewer | 凭证过账、关账、银行对账确认、敏感财务复核 | 被授权工作区 | 复核自己制单，越范围代批 |
| Cashier | 收付款登记、核销提案、银行交易登记 | 指定资金账户 / 工作区 | 不经政策直接更改科目、抹除核销历史 |
| DonationOperator | 捐赠人 / 捐赠单制单、普通收据操作 | 被授权工作区 | 自动签发法定财政票据、越权过账 |
| Auditor | 审计、已授权账簿 / 报表只读及受控导出 | 显式工作区 / 部门 | 任何交易写入、任意全租户导出 |
| IntegrationOperator | 已批准的邮件 / provider 配置和投递操作 | 指定能力与工作区 | 读取原始密钥、改变财务事实、授予自己角色 |

同一人可有多个角色，但以“角色分配 → 权限 + 范围”元组计算，禁止把所有权限与所有范围做笛卡尔积。平台管理员、Keycloak 管理员和 AI 模型均不自动成为任何公司的会计。

## 2. 操作目录与授权依据

| 操作编码示例 | 人员 / 机器 | 资源与附加检查 |
| --- | --- | --- |

| organization.members.invite / suspend | 治理角色 | 目标成员同租户、同公司，不能越权授予敏感权限 |
| organization.roles.assign | 治理角色 + 敏感授予政策 | 授予者拥有授权范围；敏感角色独立审批 |

| finance.period.close / reopen | 财务复核角色 | 截止水位、对账结论、关闭版本、原因 |
| finance.bank.reconcile / undo | 财务复核角色 | 对账区间、交易集合、差异、关闭期间 |

实际目录由业务服务版本化发布，Organization 只允许分配已登记编码。Nuxt 菜单目录是投影，不定义 API 的允许规则。任何未登记写操作、未知机器来源或缺少资源上下文的敏感操作默认拒绝。

## 3. 审批基线

1. 草稿保存不等于审批，业务服务保存审批所绑定的单据版本或摘要。
2. 默认制单人与批准 / 过账 / 敏感付款复核人不同；首期不启用“Owner 自动免审”或静默单人模式。
3. 审批人必须在批准时拥有当前权限和范围，制单后关键字段改变使原批准失效。
4. 必须使用独立审批凭据时，记录审批对象、版本、范围、决定、人员和时间，不能只传 `Approved=true`。
5. 敏感角色分配、防止提权和最后治理管理员规则由 Organization 本地事务维护；资源金额与期间仍由业务服务校验。
6. 财务过账默认在应用用例完成授权后，再于事务内核对资源版本与领域条件；授权撤销不声称能回滚已提交事实。

## 4. 三类调用上下文

| 类别 | 身份来源 | 授权时点 |
| --- | --- | --- |
| 当前用户操作 | 已验证用户 access token / 明确代理凭证 | 接受操作前确认成员、权限与范围；关键操作访问权威接口 |
| 已接受流程的服务延续 | 获准生产者 / 消费者、原操作记录和业务事实 | 当前步骤仍验证服务权限、来源、范围和状态；不要求用户继续在职 |
| 计划任务 / 人工恢复 | 显式受限机器身份或当前人工身份 | 调度包含工作区；新的人工意图重新授权，技术重试保留业务 ID |

普通读授权缓存上限 30 秒，以授权版本与过期双重约束；事件失效丢失时应在上限内收敛。账号 / 成员停用后关键新操作不得使用陈旧授权；授权依赖故障返回可区分的失败，不放行。

## 5. 必须拒绝的案例

- 销售角色只管本人单据，库存只读角色范围是全仓，两者组合不能查看全部销售单。
- 用户能过账 W1 的凭证，但把 CompanyId 改为 W2 或提交 W2 的凭证 ID。
- 制单人拥有 Reviewer 角色后，未经独立批准尝试批准自己的原单。
- 以客户端提交的 Owner、UserId、TenantId 或旧审批摘要覆盖可信上下文。
- Google 相同邮箱但不同 issuer / sub 的账号被自动合并。
- 成员已移除，队列中的未接受用户请求仍尝试执行；与已提交收货事实的合法计价延续区别处理。
- AI 有效会话但没有 finance.journal.post，或对应模块未启用，却调用写工具。
- 只有平台管理员 / Keycloak realm 管理员身份却没有工作区业务成员资格。

以上拒绝场景映射至 P1 / P2 的 API、消息及资源测试；P0 形成规则，不代表已完成实现验证。
