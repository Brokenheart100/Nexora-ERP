# ADR 0017 — 工作区治理聚合与邀请授权

- 日期：2026-11-06。
- 状态：首期治理实现已通过本地验证；不替代 ADR 0014 的完整业务授权目标。
- 关联：[成员授权验收](../verification/p1-membership-authorization.md)、[统一授权目标](0014-authorization.md)。

## 决策

Workspace 拥有治理成员与邀请子实体，变更只能通过根方法执行。最后一位有效 Owner / 管理员属于同一一致性边界；根版本既用于数据库乐观并发，也作为授权版本。两个节点分别读取旧快照后不能都移除最后治理人员，冲突返回 409，由用户重新核对，不自动重放敏感意图。

UserAccount 独立以 `(Issuer, Subject)` 唯一映射；邮箱仅为已验证的资料快照和邀请绑定条件，不能作为合并身份的键。账号在首次成功创建工作区或兑换邀请时随本地事务建立；不假设 Keycloak 身份创建与 ERP 成员绑定可以跨库原子提交。

邀请包含角色提案、操作编号、期限、状态和一次性令牌哈希。普通邀请创建时签发令牌，含业务角色的邀请由另一位所有者批准后签发令牌并发送邮件，兑换期限从签发起算 24 小时。令牌使用 32 字节安全随机数，明文通过签发响应和邀请邮件交付，数据库保存 SHA-256。兑换要求经过验签的已验证邮箱和相同 issuer，并重新确认邀请人以及适用的审批人仍有授予权限。已接受、已撤销、过期或身份不匹配时拒绝。已有成员通过成员管理恢复。

`IApplicationAuthorization` 是纯应用端口。HTTP 的资源 policy 和应用用例都检查当前账号、成员、租户 / 工作区及操作。未知权限默认拒绝。Owner、AccessAdministrator 和 WorkspaceReader 决定工作区治理及基础访问权限。Administrator 只能管理只读成员。财务制单与凭证过账需要另行授予业务角色。

用户命令只接受已认证边界发起的进程内 `InvokeAsync`。Wolverine middleware 以 receiver 设置的 listener / ReceivedAt 元数据拒绝队列中的用户 Actor；不相信任意 UserId、UserName 或信封 header。已接受业务事实采用另外的集成契约，避免把事实延续错误地绑定到人员是否仍在职。

当前不缓存授权：停用后新检查直接读取 Organization，Reporting 每次回查明确的 `reports.workspace.read` 权限。授权变更与成员 / 邀请、审计及 Outbox 同事务提交，Reporting 只维护单调的观察水位，水位或旧投影不能放行。权威接口故障拒绝读取，返回 503。

## 取舍与后续

按工作区串行化治理变更简化了首期不变量，但成员 / 邀请数量较大时加载集合和争用需要实测，再决定拆分治理名册或独立邀请聚合；不能仅为减少加载而丢掉最后管理员约束。

公司侧栏的「团队与成员」承载邀请、成员编辑和审批。「角色与权限」从 Organization 读取内置角色及对应的权限编码。业务角色可跨财务、采购、销售组合，每个模块保留一个角色。已有成员的业务角色新增与替换按完整角色集提交，提案绑定工作区授权版本，有效期 24 小时，由另一位有效所有者审批，审批人和受益人必须不同。仅移除角色时直接撤销。提交、批准和撤销经同一治理事务写入审计与 Outbox。

自定义 BusinessRole、角色与部门 / 仓库范围元组、权益与全局身份撤销继续按计划推进。真实邮件送达、Google、协调刷新和敏感操作 step-up 各有独立验收项。
