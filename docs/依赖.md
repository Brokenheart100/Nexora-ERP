## 2. 技术选型与职责

| 决策项 | 目标方案 | 选择依据与边界 |
| --- | --- | --- |
| 后端运行时 | ASP.NET Core / .NET 10 | 与当前工程一致；不在业务域绑定预览特性 |
| 本地编排 | Aspire AppHost + ServiceDefaults | 描述资源关系、服务发现、健康与遥测 |
| 服务组织 | Monorepo，多业务服务独立构建和镜像 | 方便统一演进，同时保留独立发布边界 |
| 内部分层 | 每服务 Domain / Application / Infrastructure / Api | 依赖向内，基础设施通过端口接入 |
| 写侧建模 | 聚合、值对象、领域服务、显式状态机 | 规则由领域拥有，禁止任意实体 CRUD 写入口 |
| CQRS | Wolverine 进程内命令 / 查询分发 | 读写逻辑分离；不要求 Event Sourcing |
| 关系存储 | PostgreSQL + EF Core；查询可用显式 SQL | 首期只维护一种生产数据库提供方 |
| 消息 | Wolverine + RabbitMQ + PostgreSQL durable Inbox / Outbox | 至少一次投递下保持业务幂等 |
| 消息适配 | `WolverineFx.RabbitMQ` | 底层使用官方 RabbitMQ 客户端，不单独手写交付框架 |
| 业务 HTTP API | Wolverine.HTTP + HTTP FluentValidation | 薄端点、OpenAPI、ProblemDetails；BFF 继续负责 OIDC 会话 |
| 事务与流程 | Wolverine EF Core 事务 + Saga + 持久化调度 | 显式接入写 DbContext；不替代业务额度和并发约束 |
| 工具与验证 | JasperFx codegen / 诊断、Wolverine 消息追踪、Alba | 开发与 CI 验证框架配置及真实业务链路 |
| Web 接入 | ASP.NET Core API Gateway、YARP、Nuxt Nitro | 网关集中路由与 Bearer 校验，Nitro BFF 处理浏览器会话与 CSRF |
| 认证 | 外部 OIDC 身份提供方，默认以 Keycloak 验证 | 身份提供方负责登录；ERP 自己拥有组织和业务授权 |
| 前端 | Nuxt 4 + Vue 3 Composition API + TypeScript strict | 首期私有后台采用 CSR；独立 Web 容器 |
| 缓存 / 会话 | Redis | 缓存不是业务事实来源；会话丢失允许重新登录 |
| 附件 | S3 兼容对象存储 | 元数据和权限归所属服务，文件不存容器临时磁盘 |
| 可观测性 | OpenTelemetry；本地 Aspire Dashboard，生产独立采集与告警 | 技术链路和业务失败一起可见 |
| 部署 | 容器化；开发用 Aspire，试运行用 Compose，后续按规模上托管容器或 Kubernetes | 单机试运行不宣称高可用 |

YARP 的代理能力、Keycloak 的 OIDC 接入和 RabbitMQ 的确认机制均采用其官方文档作为实施依据；具体依赖版本在实施时锁定，不在规划阶段臆定补丁号。[YARP](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/yarp/getting-started?view=aspnetcore-10.0)、[Keycloak OIDC](https://www.keycloak.org/securing-apps/oidc-layers)、[RabbitMQ .NET](https://www.rabbitmq.com/client-libraries/dotnet-api-guide)。

### 4.1 Wolverine 全家桶清单

下列核心能力纳入首期标准，不再保留“自选 Dispatcher / 原生 RabbitMQ 手写 Outbox”的并行方案。包按所属层引用，不在每个项目无差别安装。

| 组件 / NuGet | 职责 | 放置与引入要求 |
| --- | --- | --- |
| `WolverineFx` | 进程内分发、消息处理管道、路由、失败策略、Saga 与调度运行时 | Api 组合根、Infrastructure 消息适配；Domain / Application 不引用 |
| `WolverineFx.Http` | ASP.NET Core 薄 HTTP 端点与 OpenAPI 元数据 | 业务 Api |
| `WolverineFx.FluentValidation` + `FluentValidation` | 命令 / 消息输入校验 | 组合根接入；校验器按应用输入组织，不承担领域不变量 |
| `WolverineFx.Http.FluentValidation` | HTTP 校验错误到 ProblemDetails 的映射 | Api；避免同一请求路径重复执行同一校验规则 |
| `WolverineFx.EntityFrameworkCore` | 事务中间件、EF Core Saga 持久化和 Outbox 集成 | Infrastructure / 组合根，显式配置写上下文 |
| `WolverineFx.Postgresql` | PostgreSQL 消息持久化与恢复存储 | 每服务独立数据库中的消息 schema；不启用其数据库传输替换既定 RabbitMQ |
| `WolverineFx.RabbitMQ` | 消息 broker 传输、端点与连接配置 | Infrastructure / 组合根；领域和应用层不直接调用底层 RabbitMQ 客户端 |
| `WolverineFx.RuntimeCompilation` | Dynamic / Auto 模式所需运行时代码编译支持 | 采用 6.x 时开发与 codegen 构建阶段接入；生产模式见下节 |
| `JasperFx` 及其 codegen / CLI 工具链 | 处理链代码生成、配置检查与运行诊断 | 宿主和构建工具；传递依赖按锁定版本核对，不重复强钉不兼容版本 |
| Wolverine `Tracking` / tracked sessions | 等待级联消息与调度消息、断言处理结果 | 测试工程，按核心库实际提供的 API 使用 |
| `Alba` | HTTP 请求、响应和消息后续行为的集成测试 | Api 集成测试工程，不进入生产业务层 |

Saga、重试、延时消息与 tracked sessions 属于相关运行时 / 集成能力，不能为了清单完整臆造独立的 Saga 或 Testing 包。批量处理、并发限制和消息分区按实际用例配置；首期不额外并行引入 MediatR、MassTransit 或手写通用消息框架。

组件依据：[EF Core 集成](https://wolverinefx.net/guide/durability/efcore/)、[PostgreSQL](https://wolverinefx.net/guide/durability/postgresql.html)、[RabbitMQ 官方源码文档](https://github.com/JasperFx/wolverine/blob/main/docs/guide/messaging/transports/rabbitmq/index.md)、[HTTP 校验](https://wolverinefx.io/guide/http/validation.html)、[Alba 集成测试](https://wolverinefx.net/guide/http/integration-testing.html)。

### 4.2 .NET 10、版本与代码生成

- 官方仓库当前构建目标包含 `net10.0`，可作为 .NET 10 选型依据；`main` 的代码和版本号不代表本项目已经锁定的 NuGet 发布版本。[官方构建配置](https://github.com/JasperFx/wolverine/blob/main/Directory.Build.props)。
- P1 选择已发布且支持目标运行时的稳定版本，统一校验 Wolverine 各扩展包、EF Core / 数据库提供方、FluentValidation、Alba 与 JasperFx 的依赖图，并在 `Directory.Packages.props` 和锁文件中记录精确版本。
- 采用 Wolverine 6.x 时，Dynamic / Auto 运行时代码生成需要 `WolverineFx.RuntimeCompilation`。开发允许动态编译；生产目标为构建阶段生成处理链并以 Static 模式运行，验证所有处理器与 HTTP 端点可加载，避免首次请求才生成失败。
- `codegen write` 在构建阶段可能仍需编译器支持；不能简单在所有 Release 配置剔除包后，又让同一构建阶段依赖它。区分生成、重新编译与最终发布阶段，确认生成物被编译进产物，按依赖图验证最终镜像是否包含运行时编译器。
- Aspire 运行时注入的连接名要与客户端配置一致，如 `postgres`、`rabbitmq`。代码生成与 OpenAPI 构建不应依赖生产凭据或实时启动基础设施；采用锁定版本支持的构建配置，再由真实容器验证。

上述代码生成差异以官方版本说明为准。[Wolverine 代码生成与 Aspire 注意事项](https://wolverinefx.io/guide/codegen)。

### 4.3 Marten 与生态扩展边界

Marten 和 `WolverineFx.Marten` 纳入同生态扩展清单，用于以后经 ADR 选择的 PostgreSQL 文档 / 事件存储、投影或事件溯源上下文；首期交易写模型仍为 EF Core + PostgreSQL，不要求所有服务同时使用两套持久化。

若启用 Marten，每个上下文明确唯一事实来源、事务归属、投影重建和迁移方法，不能让 EF Core 与 Marten 同时维护同一聚合的权威状态。引入时同步验证各自与 Wolverine 的兼容版本。[Wolverine Marten 集成](https://wolverinefx.net/guide/durability/marten/)。

第三方或商业的生态监控产品按部署需要另行选择；首期运维基线为 OpenTelemetry、Aspire 开发观测及生产独立采集告警。

### 4.4 认证与授权组件

| 组件 | 职责与归属 | 引入规则 |
| --- | --- | --- |
| Keycloak | 身份账号、登录、MFA、OIDC、身份会话 | P1 锁定镜像与 realm / client 配置，验证 issuer、API audience 与回调；不管理 ERP 业务角色 |
| `openid-client` | Nitro BFF 的 OIDC 客户端 | 处理发现、Code + PKCE、ID Token 校验与 RP 注销 |
| `redis` 与 Node.js `crypto` | BFF 服务端会话与保护 | Redis 保存加密会话，浏览器使用随机会话 Cookie |
| `Microsoft.AspNetCore.Authentication.JwtBearer` | 业务 API 验证 Keycloak Access Token | 检查 issuer、audience、签名、时效及必要认证信息 |
| ASP.NET Core Authorization | policy、requirement、handler、资源授权适配 | Api / Infrastructure 引用框架；Application 的授权端口和上下文保持纯应用类型 |
| Organization 授权模型与内部客户端 | 成员、角色、权限目录、范围、授权版本和决策 | 本项目业务实现；各服务不读其数据库，不把框架包当成现成业务权限系统 |
| Redis + Wolverine / PostgreSQL | 会话存储、授权短期缓存、持久化失效事件 | 复用已选基础设施；关键授权以权威接口为准，敏感业务仍保留幂等和并发控制 |

首期使用标准 OIDC / JwtBearer 和 ASP.NET Core 授权扩展点，不另选一套账号密码数据库；业务权限的权威数据只放在 Organization。Keycloak 用户标识按 `(issuer, sub)` 映射内部 UserId；ERP 的 Owner / Admin、财务角色与数据范围不靠 Keycloak realm role 同名映射。

依赖于源版本的能力须在 P1 验证：服务端会话撤销、OIDC 注销、token 状态查询、认证信息与关键操作附加验证。邮箱六位 OTP 与 Google 登录现为功能对齐要求，Keycloak 流程 / 扩展和上游 OAuth client 必须在 P1 验证；扩展不可用时保持为缺项，不能默认已有或删除需求。[Keycloak OIDC](https://www.keycloak.org/securing-apps/oidc-layers)、[ASP.NET Core 策略授权](https://learn.microsoft.com/en-us/aspnet/core/security/authorization/policies?view=aspnetcore-10.0)。

## 6. 版本锁定与升级规则

- `global.json` 统一 .NET SDK；目标框架、SDK、Aspire CLI / SDK / Hosting 包分别管理。
- `Directory.Packages.props` 集中管理 NuGet；每个工程提交 `packages.lock.json`，CI 使用 `dotnet restore --locked-mode`。
- Nuxt 目标应用统一包管理器与 `packageManager` 声明，提交 `pnpm-lock.yaml`，CI 冻结锁文件安装；Node 版本按目标 Nuxt 依赖验证。
- 基础设施与应用镜像使用明确版本，发布记录 digest，不用 `latest` 作为可复现基线。
- 升级前检查运行时、数据库提供方、Aspire 集成与消息客户端兼容性，执行相关集成、迁移、契约与恢复检查。
- Wolverine 升级同时评估消息表 / Saga schema、序列化契约、重试策略和生成代码；确认滚动部署兼容后再迁移，不能由每个应用副本并发自动变更生产 schema。
- 记录直接 / 传递依赖、SBOM、许可证与已知问题；AccountGo 源码复用按架构文档中的固定提交核查。
- 秘密配置留在秘密系统；本文只记录名称与用途，不保存密码或令牌。
